# ตั้งค่า backend ของ moshimoshi (Supabase)

ถ้าไม่ใส่ env ของ Supabase แอปจะอยู่ใน **demo mode** (ใช้ข้อมูลตัวอย่าง ไม่ต้องล็อกอิน) เหมือนเดิมทุกอย่าง
พอใส่ env ครบทั้ง 2 ตัว แอปจะเข้า **live mode** คือต้องล็อกอินก่อนเข้า `/app` กับ `/onboarding` และข้อมูลมาจาก Supabase แบบ realtime

| ไฟล์ | มีอะไร |
| --- | --- |
| `supabase/migrations/20261025000001_init.sql` | ตารางทั้งหมด, trigger, RPC, RLS, grant, realtime (รันซ้ำได้) |
| `supabase/migrations/20261108000001_guard_chat_style.sql` … `20261108000003_live_reactions.sql` | ไฟล์เพิ่มเติม รันต่อจาก init ตามลำดับเลขไฟล์ (รันซ้ำได้ทุกไฟล์) ไฟล์ `_live_reactions` เพิ่มตาราง `prompt_sames` ("เหมือนกัน!" บนเรื่องเล่าในโปรไฟล์ เห็นเฉพาะคนกดกับเจ้าของ คีย์ต้องตรงรูปแบบของ `promptKey()` และเก็บได้ไม่เกิน 10 อันต่อคนต่อโปรไฟล์), เปลี่ยน primary key ของ `chat_message_sames` เป็น id สุ่ม (กันไม่ให้ event ลบบอกคนอื่นว่าใครกดในแชทส่วนตัว), ห้ามกดข้ามการบล็อกหรือตอนถูกพักบัญชี และเปิด realtime ให้ `chat_message_sames`, `daily_answer_sames`, `prompt_sames` ถ้ายังไม่ได้รัน แอปยังใช้งานได้ปกติ แค่ปฏิกิริยาเหล่านี้จะขึ้นให้อีกฝ่ายตอนรีเฟรช และ "เหมือนกัน!" บนเรื่องเล่าจะเก็บไว้ในเครื่องเหมือนเดิม |
| `supabase/migrations/20261108000004_chat_images.sql` | ส่งรูปในแชท 1:1 (บันไดความไว้ใจ ขั้น 2): ปลดล็อกเมื่อทั้งสองคนเปิด `consent_media` ของตัวเอง, ที่เก็บรูปแบบ private `chat-images` (`<chat id>/<uuid>-<กว้าง>x<สูง>.jpg`, JPEG ไม่เกิน 1.5MB), ข้อความชนิด `image`, จำกัด 30 รูปต่อชั่วโมง และ `admin_remove_chat_image` สำหรับรูปที่ถูกรายงาน (ไฟล์ต้องลบผ่าน Storage API เพราะลบแถวใน storage ตรงๆ ไม่ได้) ส่วนใครเปิดดูหรือลบไฟล์ได้ ให้ดูแถว 0005 ซึ่งตั้งสิทธิ์ใหม่แทนของไฟล์นี้ **ถ้ารันไฟล์นี้ซ้ำ ต้องรัน 0005 ต่อทันทีทุกครั้ง** ไม่อย่างนั้นสิทธิ์ของรูปจะกลับไปเป็นแบบของ 0004 โดยไม่มี error เตือน (ทุกคนในแชทกับแอดมินเปิดได้ทุกไฟล์, คนส่งลบรูปที่ถูกรายงานได้, ไม่มีเพดานอัปโหลด, ข้อความรูปไม่ต้องมีไฟล์จริง และยกเลิกส่งแล้วได้โควตาคืน) |
| `supabase/migrations/20261108000005_chat_images_hardening.sql` | รันต่อจาก 0004 (รันซ้ำได้ และต้องรันซ้ำทุกครั้งที่รัน 0004 ซ้ำ) ปิดช่องโหว่ของรูปในแชท: **เปิดดูไฟล์** (คุม `list()`, signed URL, download และไฟล์ที่ `remove()` ลบได้) ได้แก่ คนอัปโหลดเสมอ, อีกฝั่งในแชทเฉพาะตอนที่ยังมีข้อความรูปชี้ไฟล์นั้นอยู่และไม่มีใครบล็อกใคร, แอดมินเฉพาะรูปที่อยู่ในรายงาน (`reports.message_body` ตรงกับ path) **ลบไฟล์** ได้แก่ คนอัปโหลด กับแอดมินสำหรับรูปที่ถูกรายงาน แต่ถ้ามีรายงานที่ยังเปิดอยู่เกี่ยวกับรูปนั้นและชี้มาที่ตัวเอง จะลบไม่ได้ แอดมินก็เช่นกัน (ตอนนั้น `remove()` คืนรายการว่างโดยไม่มี error และไฟล์อยู่ต่อให้ทีมงานคนอื่นตรวจ) **อัปโหลด** ใช้เงื่อนไขเดิม และไฟล์ของเราที่อัปโหลดในชั่วโมงที่ผ่านมาและยังเก็บอยู่ต้องไม่ถึง 40 ไฟล์ ใน 24 ชั่วโมงไม่ถึง 200 ไฟล์ (นับเฉพาะไฟล์ที่ยังอยู่ ลบแล้วไม่นับ เกินแล้ว Storage ตอบ 403) และอัปโหลดซ้ำลง path ที่มีข้อความรูปหรือรายงานชี้อยู่ไม่ได้ (กันไม่ให้ใครใส่ไฟล์อื่นแทนรูปที่ส่งไปแล้ว หลังไฟล์เดิมหายไป) **ข้อความรูป** ต้องชี้ไฟล์ที่คนส่งอัปโหลดเสร็จแล้วและไม่มีรายงานชี้ path นั้น (รูปที่ถูกรายงานส่งกลับมาหลังยกเลิกส่งไม่ได้ และรูปที่ทีมงานเอาลงแล้วส่งซ้ำไม่ได้ แม้ลบไฟล์ไม่สำเร็จ) ไฟล์หนึ่งใช้ได้ข้อความเดียว `body` ที่ไม่ใช่ path ถูกรูปแบบจะไม่ผ่าน ข้อความชนิดอื่นที่ `body` เป็น path รูปก็ส่งไม่ได้ (แถวเก่าไม่ถูกเช็ก) และส่งได้ 30 รูปต่อชั่วโมง นับจาก log ที่ยกเลิกส่งแล้วก็ไม่ลด (error `image_rate_limited`) **บล็อก** แล้ว `consent_media` ของทั้งสองคนในทุกแชทที่มีร่วมกันจะถูกปิด ตอนรันไฟล์นี้จะปิดให้คู่ที่บล็อกกันอยู่ก่อนแล้วด้วย `admin_list_reports` ตั้ง `message_removed` ให้รูปในแชทที่ทีมงานลบแล้ว (ข้อความกลายเป็น `system` ที่ยังมี `user_id`) และ `admin_remove_chat_image` ไม่ให้แอดมินเอารูปของตัวเองลง (error `own_report` ให้ทีมงานคนอื่นทำแทน) **ก่อนรัน** ให้รัน query อ่านอย่างเดียวที่หัวไฟล์ 0005 ก่อน และอย่าเปิด versioning ให้ bucket `chat-images` ช่องที่ยังเหลือคือ signed upload URL ซึ่งเลี่ยงข้อห้ามอัปโหลดทั้งหมดนี้ได้ (ดู §7) |
| `supabase/migrations/20261108000006_rooms_and_blocks.sql` | รันต่อจาก 0005 (รันซ้ำได้ และต้องรันซ้ำทุกครั้งที่รัน init ซ้ำ เพราะ init เขียน policy `room_messages_insert` แบบเดิมกลับมา) **แชทในห้อง** ส่งได้เฉพาะสมาชิกของห้องนั้น (มีแถวของเราใน `room_members`) คือเข้าห้องก่อนแล้วค่อยคุย ออกจากห้องแล้วส่งไม่ได้อีก ข้อความเดิมยังอยู่ และทุกคนที่ล็อกอินยังอ่านแชทห้องได้เหมือนเดิม ห้องนั่งเล่นก็ต้องเข้าก่อนเหมือนห้องอื่น การ์ดต้อนรับที่ฐานข้อมูลเขียนเองยังขึ้นตามปกติ การลบข้อความโดยทีมงานยังใช้ได้ และคนที่ถูกพักบัญชียังส่งไม่ได้เหมือนเดิม (`room_messages_not_suspended`) คนที่ไม่ได้อยู่ในห้องจะได้ error RLS ธรรมดา (`new row violates row-level security policy for table "room_messages"`) สมาชิกที่ถูกพักจะได้ error ที่มีชื่อ policy `room_messages_not_suspended` แต่คนที่ถูกพักและไม่ได้อยู่ในห้องจะได้แบบธรรมดา (เช็กเรื่องสมาชิกก่อน) **`my_blocked_people()`** คืนรายชื่อคนที่เราบล็อกไว้ ใหม่สุดก่อน (`user_id, name, color, face, accessory, blocked_at`) สำหรับหน้า ฉัน → ตั้งค่า → คนที่บล็อกไว้ เพราะ `profiles` ซ่อนคนที่บล็อกกันทั้งสองทาง ฟังก์ชันอ่านเฉพาะแถว `blocks` ที่เราเป็นคนบล็อกและไม่รับพารามิเตอร์ จึงบอกใครไม่ได้ว่าใครบล็อกใคร เรียกได้เฉพาะคนที่ล็อกอิน (anon เรียกไม่ได้) การปลดบล็อกยังเป็นการ `delete` แถวของเราใน `blocks` เหมือนเดิม ช่องที่ยังเหลือ: ถ้าเราบล็อกคนที่บล็อกเราไว้ก่อน รายชื่อนี้จะเห็นชื่อและหน้าตาปัจจุบันของเขา (ถ้าซ่อนไว้ก็เท่ากับบอกว่าเขาบล็อกเรา และชื่อนี้ก็อยู่ในการ์ดต้อนรับในห้องที่ทุกคนอ่านได้อยู่แล้ว) |
| `supabase/seed.sql` | ห้อง 8 ห้อง, รอบคุย 4 วันนับจากวันที่รัน (เวลาไทย), คำถามวันนี้ของแต่ละห้อง ไม่มีคนหรือคำตอบปลอม |
| `src/lib/database.types.ts` | type ของ schema สำหรับ `createClient<Database>()` |

> "รันซ้ำได้" แปลว่ารัน migration ไฟล์เดิมอีกรอบแล้วไม่พัง แต่ไฟล์นั้นจะเขียน policy, ฟังก์ชัน และ constraint ของตัวเองทับของที่ไฟล์เลขมากกว่าแก้ไว้ ถ้ารันไฟล์ไหนซ้ำ ให้รันทุกไฟล์ที่เลขมากกว่าต่อตามลำดับจนถึงไฟล์ล่าสุด

## 1. ลง schema

แนะนำให้สร้างโปรเจกต์ที่ region **Southeast Asia (Singapore)** เพราะใกล้ผู้ใช้ไทยที่สุด

**ผ่าน Supabase MCP (วิธีหลัก)**

1. `apply_migration` ตั้งชื่อ `init` แล้วใส่เนื้อหาทั้งไฟล์ `20261025000001_init.sql`
2. `execute_sql` ใส่เนื้อหา `seed.sql`
3. `get_advisors` ทั้งแบบ `security` และ `performance` ไม่ควรมีปัญหาเกี่ยวกับตาราง ถ้ามีเตือนเรื่องการตั้งค่า Auth (เช่น leaked password protection) ข้ามได้ เพราะเราไม่ได้ใช้รหัสผ่าน
4. `generate_typescript_types` แล้วเทียบกับ `src/lib/database.types.ts` ถ้าต่างกันให้ใช้ของที่ generate ออกมา

**ผ่าน CLI (ทางเลือก)** `supabase link --project-ref <ref>` แล้ว `supabase db push` จากนั้นรัน `seed.sql` ใน SQL Editor ถ้ารันเครื่องตัวเองด้วย `supabase db reset` ตัว CLI จะรัน seed ให้เอง

> รอบคุยใน seed นับวันจาก "วันที่รัน" ถ้ารันซ้ำวันหลังจะได้ชุดใหม่ของวันนั้นเพิ่ม (ไม่ซ้ำของเดิม) ส่วนคำถามวันนี้จะใส่ให้เฉพาะวันที่รัน ถ้าจะเปลี่ยนคำถามทุกวันต้องเพิ่มแถวใน `daily_questions` เอง หรือตั้ง pg_cron

## 2. Environment variables

สร้าง `.env.local` ที่ root ของโปรเจกต์ (Vite ไม่ส่งไฟล์ `*.local` ขึ้น build และไม่ควร commit)

```bash
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxxxxxxx
```

หาได้ที่ **Project Settings → API Keys** ใช้ได้เฉพาะ publishable key เท่านั้น **ห้ามใส่ secret / service_role key ในฝั่ง client เด็ดขาด**
ตอน deploy ให้ใส่ตัวแปรชุดเดียวกันในหน้า env ของโฮสต์ที่ใช้

## 3. ตั้งค่า Auth ใน Dashboard

### URL

**Authentication → URL Configuration**

- Site URL: โดเมน production เช่น `https://moshimoshi.app`
- Redirect URLs: `http://localhost:5173/**` และ `https://<โดเมน-production>/**`

### Email OTP (รหัส 6 หลัก)

1. **Authentication → Sign In / Providers → Email** เปิด Email provider แล้วตั้ง **Email OTP Length = 6** อายุรหัส 10–60 นาทีก็พอ
2. **Authentication → Emails → Templates** แก้ template **Magic Link** ให้มี `{{ .Token }}`
   และแก้ **Confirm signup** ด้วย เพราะคนที่สมัครครั้งแรกจะได้ template นี้แทน (ถ้าเปิด Confirm email ไว้)

```html
<h2>รหัสเข้า moshimoshi ของคุณ</h2>
<p style="font-size:28px;letter-spacing:6px"><b>{{ .Token }}</b></p>
<p>ใส่รหัสนี้ในแอปภายในไม่กี่นาทีนะ ถ้าไม่ได้ขอรหัส ไม่ต้องทำอะไร ปล่อยผ่านได้เลย</p>
```

ฝั่ง client: `signInWithOtp({ email })` แล้วตามด้วย `verifyOtp({ email, token, type: 'email' })`

### Google

1. Google Cloud Console → **APIs & Services → OAuth consent screen** ตั้งเป็น External ใส่ชื่อแอป อีเมลติดต่อ และ scope `openid`, `email`, `profile`
2. **Credentials → Create credentials → OAuth client ID** เลือกแบบ **Web application**
   - Authorized JavaScript origins: `http://localhost:5173`, `https://<โดเมน-production>`
   - Authorized redirect URIs: `https://<project-ref>.supabase.co/auth/v1/callback`
3. Supabase → **Authentication → Sign In / Providers → Google** เปิดใช้งาน แล้ววาง Client ID กับ Client Secret
4. ฝั่ง client: `signInWithOAuth({ provider: 'google', options: { redirectTo: location.origin + '/app' } })` ซึ่ง `redirectTo` ต้องตรงกับ Redirect URLs ข้างบน

### Rate limits

- อีเมลจาก SMTP ในตัวของ Supabase ส่งได้แค่ไม่กี่ฉบับต่อชั่วโมง ใช้ทดสอบได้อย่างเดียว ก่อนเปิดให้คนจริงใช้ต้องตั้ง **Custom SMTP** (Authentication → Emails → SMTP Settings เช่น Resend, Postmark, Amazon SES) แล้วค่อยเพิ่มเพดานส่งอีเมลใน **Authentication → Rate Limits**
- คนเดียวกันขอรหัสใหม่ได้ทุก 60 วินาที หน้า login ควรมีนับถอยหลังก่อนกด "ส่งรหัสอีกครั้ง"
- ถ้าเริ่มมีบอทสมัคร ให้เปิด CAPTCHA (Turnstile หรือ hCaptcha) ใน Authentication → Attack Protection

## 4. สิ่งที่ฐานข้อมูลทำให้เอง

- **สมัครใหม่** → สร้างแถวใน `profiles` ให้ทันที ชื่อตั้งต้นมาจากชื่อใน Google หรือส่วนหน้าของอีเมล (onboarding ควรให้ตั้งชื่อเอง) ผู้ใช้ตั้ง `is_host` ให้ตัวเองไม่ได้
- **การ์ดต้อนรับ** → ครั้งแรกที่คนที่ onboard เสร็จแล้วเข้าห้อง จะมีข้อความ `kind = 'welcome'` ขึ้นต้นด้วย "ยินดีต้อนรับ <ชื่อ> (มาครั้งแรก)" ในแชทห้อง ถ้าเข้าห้องก่อน onboard เสร็จ การ์ดจะขึ้นตอนกด onboard เสร็จ ออกแล้วเข้าใหม่จะไม่ขึ้นซ้ำ
- **กำลังหา** → ถ้าไม่ส่ง `expires_at` มา จะตั้งให้จาก `when_kind` (คืนนี้ = ถึง 06:00 พรุ่งนี้, สุดสัปดาห์ = ถึงเช้าวันจันทร์, ระบุวัน = 7 วัน, เมื่อไหร่ก็ได้ = 14 วัน) และเปิดพร้อมกันได้สูงสุด 3 โพสต์
- **ฉันด้วย** → ตรวจว่าโพสต์ยังเปิดอยู่ ไม่ใช่โพสต์ของตัวเอง ไม่ได้บล็อกกัน และยังมีที่ว่าง (`slots`)
- **ล้างโพสต์หมดอายุ** → ถ้าเปิด extension `pg_cron` (Database → Extensions) แล้วรันบล็อกท้าย migration ซ้ำ จะมี job ล้างทุก 15 นาที ถ้าไม่เปิด ฝั่ง client ต้องกรอง `expires_at > now()` เอง (ควรกรองอยู่แล้ว)

| `respond_moshi(p_chat, accept)` | ฝั่งที่ถูกทักตอบรับ (`active`) หรือปิด (`ended`) แล้วระบบจะใส่ข้อความ system ให้ |
| `mark_chat_read(p_chat)` | อัปเดต `last_read_at` ของเรา |
| `my_blocked_people()` → รายชื่อ | คนที่เราบล็อกไว้ ใหม่สุดก่อน พร้อมชื่อ สี หน้า เครื่องประดับ และเวลาที่บล็อก (ต้องรัน 0006 ก่อน) |

error จะส่งกลับมาเป็นคีย์สั้นๆ ใน `error.message` ให้ฝั่ง client แปลงเป็นข้อความไทยเอง:
`not_authenticated`, `cannot_moshi_self`, `opener_invalid`, `target_not_found`, `blocked`, `moshi_not_allowed` (อีกฝั่งตั้งรับโมชิเฉพาะคนในห้องเดียวกันหรือคนที่เคยคุย), `moshi_declined`, `moshi_rate_limited` (เกิน 30 คนต่อวัน), `chat_not_found`, `not_allowed`, `chat_not_pending`, `intent_limit`, `intent_full`, `intent_closed`, `own_intent`, `intent_not_found`

## 6. หมายเหตุสำหรับฝั่ง client

- `reports` เขียนได้อย่างเดียว ให้เรียก `.insert()` โดยไม่ต่อ `.select()` รายงานข้อความในห้องส่ง `{ reporter, room_message_id, reason, details }` ฐานข้อมูลคัดลอกข้อความ คนเขียน (`target_user`) และชื่อห้องให้เอง
- ข้อความในห้องส่งได้เฉพาะสมาชิก (0006) ถ้าเพิ่งกดเข้าห้อง ให้รอ insert ของ `room_members` เสร็จก่อนค่อยส่ง ถ้า insert ข้อความแล้วได้ error RLS ให้เช็ก `my_suspended_until()` ก่อน แล้วค่อยเช็กว่ามีแถวของเราใน `room_members` ไหม (แอปขึ้นว่า "เข้าห้องก่อนถึงจะคุยในห้องได้นะ")
- ปลดบล็อก: `delete` จาก `blocks` ที่ `blocker` เป็นเรา แล้วโหลดข้อมูลใหม่ทั้งหมดแบบตอนต่อเน็ตกลับมา โปรไฟล์ โพสต์ และแชทของคนนั้นจะกลับมา (ยกเว้นเขาบล็อกเราไว้ด้วย) รายชื่อคนที่บล็อกไว้ให้อ่านจาก `rpc('my_blocked_people')` เพราะอ่านโปรไฟล์ของคนที่บล็อกไว้ตรงๆ ไม่ได้ ถ้ายังไม่ได้รัน 0006 แอปจะอ่านแค่แถวใน `blocks` (ไม่มีชื่อ คนที่ไม่รู้จักจะขึ้นเป็น "เพื่อนใหม่")
- `room_members`, `session_rsvps`, `intent_joins` และตาราง `*_sames` ใช้ insert/delete ถ้าเจอ error `23505` แปลว่ากดซ้ำ ข้ามได้ (หรือใช้ `upsert(..., { ignoreDuplicates: true })`)
- `chat_members` แก้ได้แค่ `last_read_at` กับ `consent_media` ส่วนข้อความในแชทส่งได้เมื่อแชทเป็น `active` แล้วเท่านั้น
- รูปในแชท:
  - อัปโหลดไฟล์ให้เสร็จก่อน แล้วค่อย insert ข้อความ `kind = 'image'` ที่ `body` เป็น path เดียวกัน (ฐานข้อมูลเช็กว่าไฟล์มีอยู่แล้วและเป็นของคนส่ง ใช้ path เดิมซ้ำจะได้ error `23505`) และสุ่ม path ใหม่ทุกครั้งที่ส่ง
  - อัปโหลดแล้วได้ 403 แปลว่ารูปยังล็อกอยู่ (ยังไม่ยินยอมทั้งคู่, แชทไม่ `active`, มีการบล็อก, ถูกพักบัญชี) เกินเพดานอัปโหลด หรือ path นั้นมีข้อความรูปหรือรายงานชี้อยู่แล้ว (ข้อหลังนี้ไม่เกิดถ้าสุ่ม path ใหม่ทุกครั้ง)
  - ถ้า insert ข้อความรูปพังเพราะเน็ต (ไม่รู้ว่าเข้าไปแล้วหรือยัง) อย่าเพิ่งลบไฟล์ ให้เช็กก่อนว่ามีข้อความที่ `body` เป็น path นั้นแล้วหรือยัง ถ้าข้อความเข้าไปแล้วแต่ไฟล์ถูกลบ รูปนั้นจะเปิดไม่ได้ถาวร เพราะอัปโหลดกลับลง path เดิมไม่ได้แล้ว ไฟล์ที่ค้างโดยไม่มีข้อความชี้ คนอื่นเปิดไม่ได้อยู่แล้ว (รองานล้างไฟล์ใน §7)
  - ถ้า `remove()` คืนรายการว่างโดยไม่มี error แปลว่าไฟล์ถูกเก็บไว้ให้ทีมงาน (มีรายงานที่ยังเปิดอยู่เกี่ยวกับรูปนั้นชี้มาที่เรา) หรือไฟล์ไม่มีอยู่แล้ว ไม่ใช่ความผิดพลาด แยกสองกรณีได้ด้วย `exists(path)` (หน้าแอดมินทำแบบนี้)
  - signed URL ที่ออกไปแล้วยังเปิดได้จนหมดอายุ คนขอเป็นคนกำหนดอายุลิงก์เอง (ฝั่งเซิร์ฟเวอร์ไม่มีเพดาน) policy ตัดไม่ได้ มีแต่การลบไฟล์ แอปจึงเลิกใช้ลิงก์ที่จำไว้ของแชทนั้นทันทีที่ `consent_media` ของใครในแชทถูกปิด (รวมตอนบล็อก) แล้วขอใหม่ ซึ่งเซิร์ฟเวอร์จะไม่ให้ถ้ามีการบล็อก
  - signed upload URL (`createSignedUploadUrl`) เช็กสิทธิ์ครั้งเดียวตอนออก แล้วตอนอัปโหลดจริง Storage ใช้สิทธิ์ service role ได้นานถึง 2 ชั่วโมง จึงไม่โดนเพดานอัปโหลดและข้อห้ามอัปโหลดซ้ำ และ token แบบ upsert ที่ออกไว้ตอน path ยังว่าง จะเขียนทับรูปที่ส่งไปแล้วหรือรูปที่เก็บไว้ให้ทีมงานได้ แอปใช้แค่ `upload()` แบบ `upsert: false` ช่องนี้ยังไม่ได้ปิด (ดู §7)
- ข้อความที่ยังไม่อ่าน = ข้อความของอีกฝั่งที่ `created_at > last_read_at` ของเรา
- สถานะออนไลน์: อัปเดต `profiles.last_seen_at` ทุก ~1 นาทีตอนเปิดแอป view `room_stats` นับคนที่เห็นภายใน 5 นาทีเป็น online
- คำถามวันนี้: เลือกแถวล่าสุดของห้อง (`day <= วันนี้`) แทนการหาแถวของวันนี้พอดี แอปจะได้ไม่ว่างถ้ายังไม่ได้ใส่คำถามใหม่
- คนที่บล็อกกันจะมองไม่เห็นโปรไฟล์กัน ข้อความในห้องที่มาจากคนที่ดูโปรไฟล์ไม่ได้ควรซ่อนไว้
- ไม่มีการกรองเนื้อหาข้อความ (founder ตัดสินใจแล้ว) มีแค่จำกัดความยาว
- ตัวเลือก "อื่นๆ" ที่ผู้ใช้พิมพ์เองไม่ต้องแก้ schema: เรื่องที่ชอบเก็บใน `profiles.tags`, `profiles.loves` และ `intents.tag_id` เป็น `custom:<ข้อความ>` (อ่านด้วย `tagOf()` ใน `src/data/tags.ts`), คำถามที่ตั้งเองเก็บใน `profiles.prompts` เป็น `{ "promptId": "own", "question": "…", "text": "…" }` ส่วนสไตล์การคุยเก็บข้อความตรงๆ ใน `profiles.chat_style`

### ลบบัญชีผู้ใช้

ไฟล์รูปในแชทไม่ได้ผูก foreign key กับบัญชี ถ้าลบผู้ใช้เลย ข้อความจะหายตาม cascade แต่ไฟล์ใน `chat-images` จะค้างอยู่ตลอด ซึ่งขัดกับนโยบายความเป็นส่วนตัวที่บอกว่าข้อความที่ส่งจะถูกลบไปด้วย ให้ทำตามลำดับนี้

1. **ก่อนลบ** หารายชื่อไฟล์ใน SQL Editor: รูปที่คนนั้นอัปโหลดในทุกแชท กับทุกไฟล์ในแชทที่จะหายไปพร้อมเขา (แชทที่ `chats.requested_by` เป็นเขาจะถูกลบทั้งแชท ต้องหาตอนนี้ เพราะลบแล้วจะไม่รู้ว่าโฟลเดอร์ไหนเป็นของแชทไหน) ไม่รวมรูปที่อยู่ในรายงาน ซึ่งเก็บไว้กับรายงาน

   ก่อนเชื่อผลว่า "ไม่มีไฟล์" ให้เช็กก่อนว่า role ของ SQL Editor ข้าม RLS ได้: `select rolbypassrls from pg_roles where rolname = current_user;` ต้องได้ `true` และ `select count(*) from storage.objects where bucket_id = 'chat-images';` ต้องไม่เป็น 0 (ถ้ามีรูปอยู่จริง) ถ้าไม่ผ่าน query ข้างล่างจะคืนรายการว่างโดยไม่มี error ให้หารายชื่อไฟล์ด้วยสคริปต์ที่ใช้ service key แทน

   ```sql
   select o.name
   from storage.objects o
   where o.bucket_id = 'chat-images'
     and (
       o.owner_id = '<user-uuid>'
       or split_part(o.name, '/', 1) in (select c.id::text from public.chats c where c.requested_by = '<user-uuid>')
     )
     and not exists (select 1 from public.reports r where r.message_body = o.name);
   ```

2. ลบไฟล์ตามรายชื่อนั้นผ่าน Storage API ด้วย service key จากสคริปต์ฝั่งเซิร์ฟเวอร์หรือ Edge Function เท่านั้น (`supabase.storage.from('chat-images').remove(names)` ครั้งละไม่เกิน 1,000 ชื่อ) หรือลบในหน้า Storage ของ Dashboard ใช้ session แอดมินในแอปไม่ได้ เพราะแอดมินเปิดและลบได้แค่รูปที่ถูกรายงาน และห้าม `delete from storage.objects` ตรงๆ (ถูกบล็อกไว้ และต่อให้ลบแถวได้ ตัวไฟล์ก็ยังค้าง)
3. แล้วค่อยลบผู้ใช้ที่ **Authentication → Users**

รูปที่ถูกรายงานเก็บไว้กับรายงานไปก่อน แล้วลบด้วยวิธีเดียวกันเมื่อหมดระยะเก็บรักษาของรายงาน ถ้าเคยลบบัญชีไปแล้วโดยไม่ได้ทำขั้นนี้ ไฟล์ที่เขาอัปโหลดยังหาเจอด้วย `owner_id` (uuid เดิมยังอยู่) แต่ไฟล์ของอีกฝั่งในแชทที่หายไปแล้วต้องรอให้งานล้างไฟล์ข้างล่างเก็บ

### ยังไม่ได้ทำ: ล้างไฟล์รูปที่ไม่มีข้อความชี้

ไฟล์ใน `chat-images` ที่ไม่มีข้อความชี้จะค้างอยู่ตลอด คนอื่นเปิดไม่ได้ (เปิดได้แค่คนอัปโหลด) แต่กินพื้นที่ไปเรื่อยๆ เช่น ส่งไม่สำเร็จแล้วลบไฟล์ไม่ทัน, ยกเลิกส่งหรือทีมงานลบข้อความแล้วการลบไฟล์พลาด, ไฟล์ของบัญชีที่ลบไปโดยไม่ได้ทำตามขั้นข้างบน และไฟล์ที่อัปโหลดผ่าน signed upload URL ที่ออกไว้ก่อน (สิทธิ์กับเพดานอัปโหลดเช็กแค่ตอนออก URL ดูหัวข้อถัดไป)

### ยังไม่ได้ทำ: ปิดช่อง signed upload URL

policy ของ `chat-images` เช็ก signed upload URL แค่ครั้งเดียวตอนออก (`createSignedUploadUrl`) พอถึงตอนอัปโหลดจริง (`uploadToSignedUrl`) Storage เขียนไฟล์ด้วยสิทธิ์ service role ซึ่งข้าม RLS ทั้งหมด และ token ใช้ซ้ำได้จนหมดอายุ 2 ชั่วโมง ผลคือ

- token แบบ upsert ที่ออกไว้ตอน path ยังว่าง เขียนทับไฟล์ที่ path นั้นได้ แม้รูปจะส่งไปแล้ว หรือถูกเก็บไว้ให้ทีมงานเพราะมีรายงาน (ลบไม่ได้ แต่ทับได้) จึงเปลี่ยนรูปที่ถูกรายงานก่อนทีมงานเปิดดูได้
- token แบบธรรมดาอัปโหลดกลับลง path เดิมได้หลังไฟล์ถูกลบ ข้ามข้อห้ามอัปโหลดซ้ำลง path ที่มีข้อความหรือรายงานชี้
- token ที่ออกไว้ล่วงหน้าไม่โดนเพดาน 40 ไฟล์ต่อชั่วโมง / 200 ไฟล์ต่อวัน และยังอัปโหลดได้หลังอีกฝั่งปิดยินยอม บล็อก หรือถูกพักบัญชี

ทำได้เฉพาะกับ path ที่เลือกไว้ก่อนจะมีข้อความชี้ ในทางปฏิบัติจึงเป็นรูปของคนส่งเอง (อีกฝั่งรู้ path ล่วงหน้าไม่ได้ เพราะสุ่มใหม่ทุกครั้ง) และต้องเขียนสคริปต์เอง แอปไม่ได้ใช้ signed upload URL

Storage เวอร์ชันที่ยังไม่มี supabase/storage PR #1392 มีช่องคล้ายกันแม้ไม่ใช้ signed URL: อัปโหลดธรรมดาถูกเช็กแค่ก่อนไฟล์เริ่มส่ง แล้วเขียนจริงด้วยสิทธิ์ service role ถ้าเริ่มอัปโหลดสองครั้งพร้อมกันลง path ใหม่เดียวกัน ครั้งหลังเขียนทับรูปที่ส่งไปแล้วหรือรูปที่ถูกเก็บไว้ได้ RLS ปิดไม่ได้ วิธีเช็กเวอร์ชันบน staging: อัปโหลด `upsert: false` สองครั้งพร้อมกันลง path ใหม่เดียวกัน เวอร์ชันที่แก้แล้วจะปฏิเสธหนึ่งในนั้น
